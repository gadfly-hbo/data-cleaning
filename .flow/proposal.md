# M9 提案：认证强化

> 来源：用户指令「/dev-flow M9」，未附范围说明。开工时以 AskUserQuestion 询问 M9 范围，用户未作答，按推荐方案继续（流程规则：可逆、范围内的假设可采，需明示——范围假设取自 backlog 推荐项「认证强化」）。proposal 较薄，history 已注明。

## 决策（本期）

**M9 = 认证强化**，三个部分，延续 M6/M7 认证线：

1. **API-key 服务认证**：面向脚本/外部工具调用 OpenAPI 风格场景。形态：admin 为用户签发 API key（`POST /api/users/:id/apikeys` 或独立端点），key 前缀可识别（如 `dck_`）、只显示一次（哈希存储，同 argon2id 或 SHA-256——选型进 GRILL）、可撤销（启用/停用/删除）、请求头 `x-api-key` 认证，与 cookie session 并存（API-key 优先）。权限继承用户角色（复用现有 canRead/canWrite 守卫，零改动业务端点）。入审计（apikey_create/revoke）。
2. **密码策略强化**：现状仅长度 ≥8。本期：复杂度规则（至少两类字符集——避免过度策略破坏本地工具可用性，具体进 GRILL）、重置密码时可强制下次登录改密（`must_change_password` 标志 + 登录响应带标志 + 前端强制跳改密页）、失败登录限流（同一用户名连续失败 N 次锁 M 分钟，内存计数即可——本地单机无需 Redis）。admin 建号/重置时审计已有，不变。
3. **会话管理增强**：现状 7 天固定 TTL、登出=删 cookie。本期：管理员可查看/吊销活跃会话（session 记录表——签发时记 jti 入库，验证时查表，吊销即删行）、会话列表入用户管理视角（admin 看全部，用户看自己）；session key 轮换不在本期（重建即全员登出，破坏性操作，留待运维需要时手动）。

## 约束（继承，全部沿用）

- 许可证硬门：新依赖必须过许可证检查。本期**预计零新依赖**（argon2id/@node-rs/argon2 已有，限流/会话表纯代码）；若 PRD 想加依赖先过门。
- 密钥哈希存储，绝不回显原文；API key 只显示一次；日志不打印 key。
- 修复/完成声明必须有 grep/diff 证据；批量编辑后先验证。
- 最小 diff；不顺手重构。
- 引擎边界声明不变；verify gate 沿用 M8 全量命令。
- 认证变更不得破坏现有 29 个 web 测试 + 66 个 api 测试（会话/Cookie 路径全兼容）。

## 明确不做（本期外）

- 协作/跨用户分享（独立里程碑）
- OAuth/SSO/LDAP（本地单机产品定位不支撑）
- docker 首次真实构建、PG/MySQL 真实验证（环境受限，README 已披露）
- web 用户管理页（M8 已声明不做；API-key 管理本期也走 API + 文档，不做 UI——若 GRILL 发现成本极低再议）
